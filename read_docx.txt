1. Resumen Ejecutivo y Propósito
1.1 Descripción del Sistema
NEXUS Observatory es una plataforma de software avanzado y ecosistema modular diseñado para proveer observabilidad, monitoreo financiero y evaluación cualitativa sobre aplicaciones impulsadas por Modelos de Lenguaje de Gran Escala (LLMs). A diferencia de los monitores de hardware tradicionales, el sistema se enfoca en auditar entidades no deterministas y comportamientos probabilísticos generados por la Inteligencia Artificial.
1.2 Objetivos Principales y Casos de Uso
El propósito central de la plataforma es brindar a ingenieros y CTOs una visibilidad transparente (Glass-Box) sobre sus sistemas de IA. Sus principales aplicaciones prácticas incluyen:
Trazabilidad y Control Financiero: Captura latencias, conteo exacto de tokens y costos por invocación (LLMOps) a través de telemetría estructurada.
Evaluación y Auditoría de Código (Code Review): Análisis estático impulsado por IA para auditar código fuente, detectando vulnerabilidades de seguridad, defectos de mantenibilidad y calculando una métrica de calidad.
Chat Contextual con Repositorios (Repo Agent): Ingresa, vectoriza y permite interactuar conversacionalmente con todo un repositorio (RAG) en tiempo real, reteniendo contexto de sesiones pasadas.
A/B Testing Empírico: Permite enfrentar distintos prompts, hiperparámetros o modelos (ej. Groq vs. OpenAI) bajo las mismas condiciones para determinar científicamente cuál genera la salida óptima.
2. Arquitectura del Sistema y Flujo Lógico
El núcleo de NEXUS implementa un patrón arquitectónico desacoplado moderno (Frontend/Backend) integrando bases de datos vectoriales locales para RAG y pipelines de observabilidad de terceros.
2.1 Diagrama de Componentes (Flujo de Datos)
[ Usuario / Desarrollador ]     │ (Solicitud UI: Revisión de código, Chat de repositorio)    ▼[ Frontend SPA (React 18 / TypeScript / Tailwind) ]    │ (Peticiones HTTP REST / JSON)    ▼[ Backend API Gateway (FastAPI / Python 3) ] ◄────────────────┐    │                                                         │    ├─► [ Motores de Inferencia (LLMs) ]                      │ (Registro Telemetría)    │        ├─► Groq (Llama 3, Mixtral)                      │    │        └─► OpenAI (GPT-4o)                              │    │                                                         │    ├─► [ Bases de Datos & Almacenamiento ]                   │    │        ├─► ChromaDB (Base de datos vectorial RAG)       │    │        └─► SQLite / PostgreSQL (Persistencia sesiones)  │    │                                                         │    ▼                                                         │[ Capa de Observabilidad & Instrumentación ] ─────────────────┘    ├─► LangSmith (Trazas LangChain)    ├─► Helicone (Gateway de costos y cache)    ├─► Arize Phoenix / Weave (Métricas locales)    └─► Weights & Biases (Registro de experimentos)
2.2 Ciclo de Ejecución Paso a Paso
Recepción de Datos: El cliente envía parámetros operativos (ej. URL del repositorio Git a clonar, bloque de código a auditar).
Procesamiento de Contexto (Vectorización): Si aplica, el backend clona el repositorio, procesa los archivos mediante Sentence Transformers y los indexa en la base de datos ChromaDB.
Invocación al Motor (Inferencia): El core arma el prompt optimizado y lo despacha al LLM configurado, interceptando la solicitud para registrar el timestamp de inicio.
Instrumentación y Respuesta: La API recibe la generación, calcula los tokens consumidos y la latencia. Envía esta data a la pila de observabilidad y devuelve la carga útil al cliente.
Visualización Reactiva: El frontend parsea el JSON y lo despliega mediante gráficos interactivos de Recharts y editores de código (Monaco Editor).

4. Limitaciones del Sistema y Gestión de Riesgos
⚠️ Consideraciones Críticas de Operación
Dependencia de Proveedores Nube: La continuidad operativa depende directamente del uptime de las APIs de Groq, OpenAI y plataformas como LangSmith o Helicone.
Cuellos de Botella en RAG Local: La indexación y carga de embeddings para repositorios masivos (+5,000 archivos) en ChromaDB puede saturar el uso de memoria RAM si se ejecuta localmente sin hardware dedicado.
Naturaleza Probabilística: Los reportes de evaluación de código (A/B Testing y Code Review) están sujetos a las alucinaciones inherentes de los modelos de IA; los resultados requieren verificación humana técnica final.
Rate Limits: El abuso de solicitudes desde la plataforma puede desencadenar bloqueos temporales por políticas HTTP 429 (Too Many Requests) de los proveedores de LLMs subyacentes.
5. Plan de Desarrollo Futuro (Roadmap)
Con el fin de mitigar las limitaciones actuales, se han priorizado las siguientes líneas de desarrollo para las próximas versiones:
Arquitectura Híbrida Uncensored (Soberanía de Datos): Integración nativa con Ollama para ejecutar modelos locales potentes sin censura y garantizar que los datos corporativos (PII y secretos de código) jamás abandonen la red local del cliente.
Integración CI/CD Directa: Acoplamiento automatizado mediante webhooks con GitHub Actions y GitLab CI para bloquear pull requests si el Code Review de NEXUS devuelve una puntuación de mantenibilidad inferior a 80/100.
Análisis de Commit (Risk Matrix): Módulo para analizar el historial histórico de commits mediante GitPython y graficar zonas de alta deuda técnica en el repositorio.
Despliegue Multi-Tenant Enterprise: Soporte avanzado para Kubernetes (K8s) orientado a vender licencias corporativas a bancos y entidades del estado, incluyendo autenticación SSO.
